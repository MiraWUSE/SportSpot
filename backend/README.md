# SportSpot — серверная часть

В этом разделе находятся база данных, серверная модерация спортивных площадок и интеграция с OpenStreetMap через Overpass API.

Разделы 1–2 описывают подготовку **нового проекта Supabase**. Порядок обновления существующего поиска приведён в §6.5.

## 1. Какие файлы нужны

```text
SportSpot/
└── backend/
    ├── README.md                              # эта инструкция
    ├── setup.sql                              # создание основной базы данных
    ├── postman/
    │   └── SportSpot.postman_collection.json  # коллекция API-тестов
    ├── sql/
    │   └── 10_overpass_integration.sql        # кеширование и лимиты поиска
    └── supabase/
        ├── config.toml                        # настройки Edge Functions
        └── functions/
            ├── moderate-spot-proposal-v1/
            │   └── index.ts                   # модерация площадок
            └── search-sports-spots-v1/
                └── index.ts                   # поиск площадок через Overpass.ch
```

- **`setup.sql`** — создаёт 8 основных таблиц, связи между ними, ограничения, правила доступа (RLS) и SQL-логику модерации.
- **`sql/10_overpass_integration.sql`** — отдельно создаёт 2 служебные таблицы и SQL-функции для кеширования и Rate Limiting. Для нового проекта запускается **после** `setup.sql`.
- **`supabase/migrations/20261128163136_search_cache_retention_and_quota.sql`** — актуальные RPC, индексы и функция очистки поиска.
- **`supabase/functions/`** — исходный код двух серверных Edge Functions.
- **`config.toml`** — включает проверку JWT для модерации (`true`) и отключает её для публичного поиска (`false`).
- **`postman/`** — проверенные запросы к опубликованному API и автоматические проверки ответов.

## 2. Как установить базу данных

1. Зайдите на [supabase.com](https://supabase.com/dashboard) и создайте **новый проект**. Data API должен быть включён.
2. Откройте проект → **SQL Editor** → **New query**.
3. Откройте файл `backend/setup.sql`, скопируйте весь код в SQL Editor.
4. Нажмите **Run**.
5. Откройте **Table Editor** и проверьте, что появились 8 основных таблиц:

   `profiles`, `spots`, `reviews`, `favorites`, `spot_proposals`, `spot_photos`, `review_photos`, `proposal_photos`.

6. Для работы функции поиска отдельно выполните `backend/sql/10_overpass_integration.sql` через SQL Editor. Он создаст две служебные таблицы в закрытой схеме `app_private`: `spot_search_quota` и `spot_search_cache`.
7. Примените [миграцию поиска](supabase/migrations/20261128163136_search_cache_retention_and_quota.sql) и настройте расписание по §6.5.

Структура основной базы и её правила доступа созданы. RLS включён для всех таблиц. Работа с фотографиями через Storage пока не настроена, поэтому их таблицы закрыты для клиентских запросов.

## 3. Как создать пользователя и модератора

1. В Supabase откройте **Authentication → Users**.
2. Нажмите **Add user** и создайте аккаунт со своим Email и паролем.
3. При создании пользователя в `profiles` автоматически появится запись: `name` будет взято из указанного имени или Email, роль — `user`.
4. Если аккаунт должен быть модератором, откройте **SQL Editor** и выполните **от имени администратора проекта**:

```sql
UPDATE public.profiles AS p
SET name = 'SportSpotModerator',
    role = 'moderator'
FROM auth.users AS u
WHERE p.id = u.id
  AND lower(u.email) = lower('EMAIL_МОДЕРАТОРА')
RETURNING p.name, p.role;
```

Вместо `EMAIL_МОДЕРАТОРА` укажите Email созданного аккаунта. В результате должна появиться одна строка с ролью `moderator`.

Обычный пользователь **не может назначить себе роль модератора** через приложение.

## 4. Как установить `index.ts` (модерацию)

**Одного `setup.sql` недостаточно.** Серверную функцию нужно опубликовать отдельно. Самый простой способ — через сайт Supabase.

### Сайт Supabase

1. Откройте свой проект → **Edge Functions**.
2. Создайте новую функцию через встроенный редактор.
3. Назовите её **точно** `moderate-spot-proposal-v1`.
4. Откройте `backend/supabase/functions/moderate-spot-proposal-v1/index.ts` и вставьте весь код в редактор функции.
5. Убедитесь, что **Verify JWT** включён.
6. Нажмите **Deploy**. Функция должна получить статус **ACTIVE**.

Функция доступна по адресу:

```text
https://ВАШ_PROJECT_REF.supabase.co/functions/v1/moderate-spot-proposal-v1
```

`PROJECT_REF` — идентификатор из адреса проекта в Supabase Dashboard. Для вызова модерации необходим JWT пользователя с ролью модератора.

## 5. Как проверить работу

**Проверка базы:** в Table Editor должны отображаться все 8 основных таблиц. Для поиска дополнительно существуют 2 служебные таблицы в `app_private`. В **Authentication → Policies** проверьте, что RLS включён.

**Проверка чтения:** в разделе **API Docs** Supabase можно выполнить GET-запросы к `spots` и `reviews`. В заголовке `apikey` используйте свой `publishable` ключ:

```text
GET /rest/v1/spots?select=*
GET /rest/v1/reviews?select=*
```

Ожидается **200 OK**. Если таблицы пустые, ответ `[]` — это нормально.

**Проверка модерации:** авторизуйтесь под аккаунтом с ролью `moderator` и вызовите Edge Function методом **POST**. Нужны заголовки `apikey` (публичный ключ), `Authorization: Bearer <JWT_МОДЕРАТОРА>` и `Content-Type: application/json`.

Пример тела запроса для одобрения:

```json
{
  "proposal_id": "UUID_СУЩЕСТВУЮЩЕЙ_ЗАЯВКИ",
  "decision": "approved"
}
```

Для отклонения:

```json
{
  "proposal_id": "UUID_СУЩЕСТВУЮЩЕЙ_ЗАЯВКИ",
  "decision": "rejected",
  "reason": "Площадка не подходит"
}
```

Если одобрение успешно, площадка появится в `spots`. При отказе заявка получит статус `rejected` и причину отказа.

**Ожидаемые ответы:** `200` — выполнено; `401` — не авторизован; `403` — нет роли модератора; `404` — заявка не найдена; `409` — заявка уже обработана. Для безопасной проверки доступа можно указать несуществующий UUID и получить `404`, ничего не создавая.

**Формат ошибок:** ошибки, сформированные самой Edge Function, возвращаются в формате {"error":{"code":"...","message":"...","request_id":"..."}}. 
Если JWT отсутствует или отклонён шлюзом Supabase до запуска функции, ответ может иметь другой формат, например {"code":"UNAUTHORIZED_NO_AUTH_HEADER","message":"Missing authorization header"}.
Это ожидаемое поведение.

## 6. Внешняя интеграция с Overpass API

SportSpot использует Overpass API для поиска спортивных площадок из OpenStreetMap.

Запросы к внешнему API выполняются через Supabase Edge Function `search-sports-spots-v1`. По архитектуре мобильное приложение должно обращаться к этой серверной функции, а не напрямую к Overpass.

### 6.1. Установка и обновление

Для нового проекта выполните §2, включая базовый SQL поиска и версионированную миграцию. Для существующего SportSpot сначала проверьте наличие таблиц app_private.spot_search_cache и app_private.spot_search_quota, затем примените только [миграцию поиска](supabase/migrations/20261128163136_search_cache_retention_and_quota.sql) в порядке из §6.5. Старые RPC сохранены для отката функции. Существующий supabase/config.toml подходит для текущего проекта. [Supabase CLI changelog](https://supabase.com/changelog/supabase-cli-config-jsonc-default).

Настройте OVERPASS_CH_KEY в Edge Function Secrets. SUPABASE_URL и SUPABASE_SERVICE_ROLE_KEY используются средой функции. В рабочем окружении эти значения остаются на сервере. Перед развёртыванием проверьте, что проект и учётная запись Overpass относятся к выбранному окружению. Verify JWT для публичного поиска остаётся выключенным.

| Переменная | По умолчанию | Допустимый диапазон |
|---|---:|---:|
| SPOT_SEARCH_OVERPASS_PER_MINUTE | 5 | 1–5 |
| SPOT_SEARCH_OVERPASS_PER_DAY | 500 | 1–500 |

Неверное значение останавливает промахи кеша с HTTP 500 до обращения к Overpass. Попадания в кеш доступны в пределах своей квоты. Эти числа — ограничения SportSpot. Тариф Overpass применяется к учётной записи и разделяется между ключами. Проверьте тариф, месячный остаток и слоты в кабинете или одним запросом status?format=json с серверным ключом. Записывайте только агрегированные лимиты. [Документация Overpass.ch](https://overpass.ch/docs), [условия Overpass.ch](https://overpass.ch/legal/terms).

### 6.2. Контракт поиска

Маршрут GET /functions/v1/search-sports-spots-v1 остаётся публичным и сохраняет ответ Android API. Для тестового проекта можно проверить такой путь:

    /functions/v1/search-sports-spots-v1?lat=0&lon=0&radius=100&sport=all

| Параметр | Описание |
|---|---|
| lat | От −90 до 90, обязателен, максимум 6 десятичных знаков |
| lon | От −180 до 180, обязателен, максимум 6 десятичных знаков |
| radius | Целое число 100–3000 метров, по умолчанию 1000 |
| sport | all, soccer, basketball, volleyball, tennis или fitness, по умолчанию all |

Ответ HTTP 200 содержит spots, count, source, attribution и cache (hit/miss). Пустой список также кешируется. Ключ v3 включает координаты, точный радиус и вид спорта, чтобы результат одной области не подменял выдачу другой. Все ответы содержат Cache-Control: no-store и X-Request-Id. Ошибки сохраняют структуру error с code, message и request_id.

| Статус | Поведение |
|---|---|
| 400 / 405 | Параметры не прошли проверку или использован метод вместо GET |
| 429 RATE_LIMITED | Отдельные проектные лимиты попаданий (300/мин) и промахов (60/мин) либо лимит Overpass |
| 500 | Ошибка серверной конфигурации |
| 503 UPSTREAM_UNAVAILABLE | Временный отказ Overpass или серверной зависимости |

В ответах 429 и 503 Retry-After передаётся целым положительным числом секунд. Проект возвращает время до конца исчерпанного окна. Для ответа Overpass используются секунды или HTTP-дата поставщика, а при недопустимом или отсутствующем заголовке — 60 секунд. Один запрос Edge выполняет максимум одну попытку к Overpass. Минутный и суточный бюджеты бронируются атомарно. Отказ любого окна не увеличивает второе.

### 6.3. Хранение и мониторинг

TTL выдачи из кеша — один час. Просроченная запись становится доступной для удаления сразу после истечения TTL. Плановый запуск ежечасно удаляет до 1000 просроченных снимков и 1000 старых счётчиков. Для известных минутных окон явно задан срок два дня, для суточного окна и прочих старых служебных счётчиков — восемь дней. При штатной работе цель — удалить ключи с координатами не позже 24 часов после истечения TTL. Просрочка работы, блокировки и начальный backlog требуют наблюдения и отдельного дренирования пакетами.

Таблицы закрыты в app_private. RPC чтения/квот доступны service_role. Функцию очистки может вызывать владелец БД; она не доступна клиентским или Edge-ролям. TTL, cache key и исходящий запрос остаются без пространственного округления.

В Edge Function Logs фильтруйте по имени search-sports-spots-v1. Собирайте счётчики по cache (hit/miss/unchecked), status и reason. Отдельно отслеживайте cache_hit_limit, cache_miss_limit, overpass_project_limit и overpass_provider_limit. Для ответа поставщика добавляются upstream_status и числовые upstream_limit/upstream_remaining, когда заголовки корректны. Сбой записи виден по cache_write=failed. Прикладная запись содержит идентификатор, время и технические признаки. Координаты, ключ кеша, авторизация и тела ответов в неё не входят. Проверьте политику системных логов gateway отдельно.

### 6.4. Проверки

CI выполняет Deno unit-тесты, PGlite и отдельный тест с 20 независимыми соединениями в изолированном PostgreSQL. Для внешнего smoke используйте тестовый проект с фикстурами. Проверьте 400, ограниченный 200, повтор того же запроса с cache=hit и наличие заголовков. Истощение квот и 429 поставщика воспроизводятся локальными двойниками. Коллекция Postman в backend/postman рассчитана на уже развёрнутое окружение. Перед ручным запуском проверьте, что у запросов выбран тестовый URL.

### 6.5. Развёртывание и откат после согласования

1. Сверьте project ref, список миграций, наличие app_private и таблиц поиска. Проверьте права владельца и наличие pg_cron. Оцените размер двух таблиц и число просроченных строк без вывода ключей. Выберите окно низкого трафика. DDL использует lock_timeout 2 с и statement_timeout 30 с. При превышении миграция откатывается, а крупный объём индексов требует отдельного согласованного плана.
2. В staging выполните версионированную миграцию по принятому журналу миграций. На уже развёрнутом проекте применяйте только файл этапа №2. Проверьте отсутствие доступа к новым RPC у anon/authenticated и наличие доступа у service_role. Убедитесь, что функция очистки вызывается владельцем. В staging создайте только синтетические записи, выполните небольшую очистку и убедитесь, что свежие записи остаются.
3. Разверните поисковую функцию из каталога backend, указав вручную проверенный staging project ref. Применяйте конфигурацию секретов из менеджера окружения. Для CLI используется команда supabase functions deploy search-sports-spots-v1 --project-ref <staging-ref>. Убедитесь, что 200/400 и тестовые 429/503 имеют ожидаемый контракт и метрики.
4. Если pg_cron подключён, создайте расписание в staging из SQL Editor под владельцем объектов поиска. Если расширение недоступно, владелец должен отдельно включить его в Dashboard или согласовать альтернативное расписание. Миграция не подключает расширение.

    ~~~sql
    select extname from pg_extension where extname = 'pg_cron';
    select cron.schedule(
      'sportspot-search-retention',
      '17 * * * *',
      'select * from app_private.spot_search_cleanup(1000)'
    );
    ~~~

5. Проверьте cron.job и cron.job_run_details под владельцем. Контролируйте последний успешный запуск и возраст самой старой просроченной записи (агрегат max(now() - expires_at) по просроченным). Первичный backlog очищайте отдельными короткими транзакциями с указанным максимумом, после согласования. Если возраст превышает 24 часа, проверьте ошибки расписания, объём и пропуски из-за блокировок. Покрытие начинается после включения и успешных запусков. [Supabase Cron](https://supabase.com/docs/guides/cron/quickstart).
6. После наблюдения в staging и отдельного разрешения повторите шаги в production. Порядок — SQL, проверка прав, Edge, проверка, затем Cron. В GitHub Actions выполняются только тесты. Для отката отключите только этот job через cron.unschedule('sportspot-search-retention') и верните предыдущую Edge Function. Сохранённые прежние RPC позволяют ей работать с текущей схемой. Не восстанавливайте удалённые просроченные ключи. Не запускайте setup.sql на рабочей БД.

## 7. Миграция избранного

Поиск получает площадки из OpenStreetMap. Многие из них отсутствуют в `public.spots`, поэтому внешний ключ `favorites.spot_id → spots.id` блокирует их сохранение. Миграция снимает этот ключ и добавляет приватный снимок площадки в `spot_snapshot`. Снимок нужен, чтобы открыть сохранённую площадку на другом устройстве.

1. Сверьте проект Supabase и текущую схему таблицы `public.favorites`. Проверьте внешний ключ на `public.spots` и политики доступа владельца. Сделайте резервную копию базы перед изменением, чтобы при ошибке можно было восстановить записи и схему.
2. После отдельного разрешения владельца один раз выполните в SQL Editor файл [SportSpotFavoritesSnapshot.sql](sql/SportSpotFavoritesSnapshot.sql) в проверенной базе. Для обновления существующей базы достаточно этого файла.
3. Проверьте, что появился столбец `spot_snapshot`, старые записи сохранились, а связь с `profiles` и политики RLS действуют. Сохраните тестовую OSM-площадку без записи в `public.spots` и откройте её детали из избранного.
4. Проверьте доступ двумя тестовыми аккаунтами через обычный клиент. Второй аккаунт не должен видеть или удалять запись первого. После попытки удаления проверьте, что запись всё ещё видна первому аккаунту. Попытка вставить запись с чужим `user_id` должна завершаться отказом. Запросы гостя без сессии не должны читать или добавлять записи.
5. Перед откатом найдите записи избранного без пары в `public.spots` и сделайте их резервную копию вместе со снимками. Старый внешний ключ можно вернуть, только когда у всех сохраняемых записей есть соответствующая площадка. При откате приложения сохраните столбец `spot_snapshot`, чтобы не потерять эти данные.
